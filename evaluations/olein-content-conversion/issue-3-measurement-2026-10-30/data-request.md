# 実測評価に必要な最小入力

まずは1記事・1種類の CSV / JSON から開始できる。3種類すべての用意や新しい認証連携は不要。データがない種類の成果は判定しない。対象記事は、以前の指定記事2本のどちらかでも、それ以外の実記事でもよい。

## 共通情報

- 対象ページ URL (必要なら計測上のパス・canonical も)。記事別に切り出しているか、サイト全体か。
- 集計期間の開始日・終了日、取得日時、集計タイムゾーン。
- 出所 (GSC / GA4 / 問い合わせ管理等) と抽出方法。匿名化・集計・除外・丸めを行った場合はその内容。
- プロパティは識別可能な仮名でよい。認証情報は不要。件数・分母・期間・記事との関係を匿名化で変えた場合は、その限界を明記する。
- 改善の前後を比較する場合は、変更日・変更内容、比較する原稿版・期間と、他の改修・キャンペーン・計測変更の有無。不明でもそのまま「不明」と記載する。

## Search Console の場合

最小列: `page`, `clicks`, `impressions` と共通情報。検索意図も評価するなら `query` 列が必要。平均掲載順位がある場合は併記する。

検索タイプ、国・端末・検索での見え方等のフィルタ、ページ合計かクエリ別か、抽出上限・欠落・匿名クエリの扱いを添える。わからない項目は不明とする。

CTR は同じ範囲のクリック合計 / 表示合計で再計算する。ページ合計とクエリ行を足さず、行 CTR を単純平均しない。クエリ行に現れない分を0件にしない。平均掲載順位を固定の現在順位とは扱わない。

## GA4 の場合

最小列: 対象記事を閲覧した `sessions` と、評価したい行動の件数。サービス遷移率を評価するなら、対象記事閲覧セッションのうちサービスへ遷移した**重複なしセッション数**が必要。

件数がイベント回数・ユーザー数・セッション数のどれか、記事閲覧後の行動に限定できているか、対象イベント名と発火条件を添える。イベント回数しかなければ、セッション遷移率とは呼ばない。単位が違う列を分母・分子にしない。

キーイベント設定時期、集計スコープ、帰属モデルと遡及期間、閾値・サンプリング・同意取得・計測変更の状態は、把握している範囲で添える。不明は不明として制限に残す。GSC のクリック数と GA4 のセッション数を同じ数とは扱わない。

## 問い合わせ集計の場合

最小項目: 期間、実問い合わせ件数、相談分類・記事テーマとの関連、前閲覧記事がわかる件数 / 不明件数、把握方法 (自己申告 / 計測 / 不明)。受注について評価する場合だけ受注件数と定義が必要。

氏名・メール・電話・顧客を特定する文章・個人識別パラメータは含めない。行ごとの生履歴ではなく必要な匿名集計でよい。前閲覧記事が不明な問い合わせを指定記事へ割り当てない。

問い合わせリンクのクリック、フォーム閲覧、送信完了イベント、管理側で確認した実問い合わせ、適合相談、受注は別段階として扱う。未計測を0件にせず、分母0の率は未定義とする。

## 受け渡し後の扱い

まず匿名化済みファイルのローカル保存先と共通情報を確認する。原データは変更せず、外部検索や Issue コメントに送信しない。この入力依頼と不足状況には実測値や顧客情報を含めない。

成功や因果関係の判定は、データを見てから都合よく設定しない。最初の観測は記述的に整理し、今後の改善検証について、同じ期間長・曜日・流入構成等の比較可能性と必要な母数・期待差を確認して条件を決める。少数例や帰属不明で条件を定められなければ成功を断定せず、必要情報を残す。
