# 正式な監査手順 (ルール版1.1)

固定ルールの正本は [audit-rules.json](audit-rules.json)。A〜Fの18項目それぞれに、対象、基準の種類、根拠取得先、問題条件、適切条件、判定不可条件、確信度の目安、改善確認方法を定義する。JSONのルール一覧だけを必須として読み、全調査資料を一括ロードしない。

各項目を次の順で判断する。

1. 記事タイプとモードから適用範囲を決める。対象外理由を本文の目的や企画要件で説明する。
2. 今回の入力版と読んだ範囲を特定する。公開画面やフォーム送信を見ていなければ動作確認済みとしない。
3. 必要な証拠を取得する。基準の出典と記事の観測を別々に引用する。原稿自体は「原稿に何が書かれているか」の証拠であり、外部主張の真偽の証拠とは限らない。
4. 問題条件・適切条件を当て、必要証拠がなければ判定不可、部分情報・矛盾なら要確認。適切な部分と未確認範囲を理由に併記する。
5. classification、状態、確信度を別々に決定し、rationaleに適用条件を記す。A-01/E-03では定義済みの`checks`ごとにも判断・根拠・制限を記す。条件の違う複数問題は同一ルール内にまとめ、18個の固定IDを増殖させない。
6. 改善の根拠と期待効果を区別する。本文の誤りの修正確認は文書検証、遷移や問い合わせへの効果は別途実測で確認する。効果未検証の修正案も提案できる。

## 安定IDと優先順位

1記事・1レポートにルールIDそのものを指摘IDとして18件を1回ずつ出す。IDは文章、出力順、重要度、見出し名から採番しない。表示はA-01〜F-02順とする。JSONにschema_version / rules_version / 原稿SHA-256または版識別子を残す。同じ根拠でも意味評価の完全一致は保証できないため、理由と根拠IDを比較する。

- `critical` / P1: 裏付けのある重大な誤情報、危険手順、虚偽サービス・恐怖営業など、読者の判断に大きく影響。
- `improvement` / P2またはP3: 具体的な不足・文脈不一致。P2は主要目的、P3は補助目的。効果の大きさは推測で優先度の根拠にしない。
- `info` / none: 観測、未確認、調査待ち。`none` / none: 適切・対象外。

各優先度には理由を添える。情報不足をcriticalにしない。確認作業の順序は別途記述できる。

## 部分確認と確認範囲

`audit-rules.json`の`assessment_scope`が単一項目の範囲、`checks`が複合項目の安定した部分定義である。

| 親ID | 部分キー | 確認範囲 |
|---|---|---|
| A-01 | audience_goal | structure: 本文・企画の想定読者と目的 |
| A-01 | observed_queries | outcome: 実クエリと想定意図の照合 |
| E-03 | static_path | structure: 静的な案内・リンク・到達 |
| E-03 | submission | behavior: 入力・送信・完了・受信の動作 |

新規1.1出力ではこれらを定義順にすべて記録する。情報不足なら該当する部分だけを判定不可にする。不要な経路なら対象外とする理由を記す。未登録の部分キーは追加しない。他の項目は単一判断のままとし、E-04だけoutcome、それ以外はstructureとして扱う。追加の分割が必要と分かってから、ルール版とテストを更新する。

親の状態は部分確認の改善推奨 → 判定不可 → 要確認 → 適切の順で集約し、すべて対象外なら対象外。親の分類・根拠はその主判断に合わせる。確認済みの部分から、未確認の部分まで確認済みにしない。たとえば静的到達が適切でも、送信未確認なら親は判定不可で、static_pathの適切は独立して残る。

## 3領域の要約

- SEO・コンテンツ品質: A、B
- コンバージョン導線品質: C、D、E
- 読者体験・信頼性: F

1.1版では領域ごとに`structure` (構造品質) と`outcomes` (実測・成果確認) を別々に表示する。複合項目は親の状態ではなく、各`checks`の範囲に分けて集約する。単一項目は上記の確認範囲を使う。各表示内の集約順は改善推奨 → 判定不可 → 要確認 → 適切、全対象外または対象なしなら評価対象外。対象なしを成果不良とは扱わない。

各表示の`check_ids`に集約対象のID (`A-01.audience_goal`等、単一項目は`B-01`等) を列挙する。領域の`unverified_checks`にはstructure / outcome / behaviorを問わず、要確認・判定不可のIDをすべて残す。送信の動作は実際の問い合わせ数ではないためoutcomesへ混ぜず、E-03.submissionと未確認一覧で表示する。構造品質が適切でも送信成功を保証しない。

これは確認範囲の分離であって採点ではない。実クエリの一致は検索者の意図の完全な証明ではなく、成果数値とも異なる。E-04の実測値と因果解釈は別に説明する。改善推奨があっても未確認一覧を省かない。

既存1.0出力は従来通り全項目の主状態で集約し、旧スキーマで検証する。過去の判断を書き換えず、新形式へ移す場合は部分確認を根拠から補い、別成果物として保存する。版番号だけ変更して未確認を適切に変えない。
